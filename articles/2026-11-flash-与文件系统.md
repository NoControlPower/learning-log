# Flash 与文件系统：从硬件约束到工程判断

> 一篇系统性笔记。**不含公司/产品信息，数字为通用设计参数。**
> 适合：写过 Flash 存储但没系统梳理过的人；被"写 Flash 为什么卡"折磨过的人。

## 0. 先分清四层

```
业务格式（字段、版本、完整性）
   ↑
文件系统 / KV / 自定义记录（组织、定位、更新、回收）
   ↑
分区（地址范围）
   ↑
存储器（NOR / NAND / RRAM / EEPROM）
```

- **存储器**决定读写、擦除、寿命、掉电等硬件约束；
- **分区**只划地址范围，不提供文件、事务或掉电保护；
- **文件系统**决定范围内怎么组织、更新、回收；
- **业务格式**决定字段含义、版本与完整性校验。

**常见混淆**：把"NVM"当成文件系统；把"分区"当成隔离；把"文件系统校验"当成业务数据可靠。

## 1. NOR 的读、编程、擦除

- 擦除后通常为 `0xFF`；编程把 1 改 0；**要恢复 1 必须擦除**。
- `0xFF → 0xF0` 合法；`0xF0 → 0xFF` 需要擦除。
- **不是每次写都要擦**：空白区可直接编程；只有复用空间才需要擦。
- 同页重复编程的限制（次数、位模式）以芯片手册为准。

**粒度概念**（典型值，具体看器件）：

| 名称 | 典型值 | 含义 |
|---|---|---|
| 页编程 | 256 B | 一次编程的最大单位 |
| 扇区擦除 | 4 KiB | 擦除的最小单位 |
| 文件系统 prog-size | 256 B | 文件系统与后端的配置契约 |
| 文件系统 cache-size | 512 B | 缓存大小，不是业务缓冲 |

**结论**：改 16 B 可能需要擦 4 KiB——这是写放大最原始的来源。

## 2. 新地址、AB 与"可靠提交"

同扇区"读到 RAM→改→擦原扇区→写回"：中途掉电 = 唯一副本丢失。
把新版本写到另一块可擦除区域能保留退路，但**不自动保证新版本完整**。

可靠交接需要：

| 信息 | 职责 |
|---|---|
| magic / 版本 / 长度 | 能否识别和解释 |
| CRC | 检测损坏（不能恢复，也不能判断新旧） |
| 序号/代次 | 判断先后（要考虑回绕） |
| 提交判定 | 候选是否完成、可被采用 |
| 旧版本保留 | 失败恢复的退路 |

顺序：保留 A → 准备 B → 写 B → 提交 → 采用 B → 回收 A。

**注意**：序号更大但未提交的 B，不能取代 A；AB 也不等于"两页"，也可以是"扇区内多记录追加"或"多扇区轮换"。

## 3. 文件与元数据

文件内容是数据；名字、目录、长度、块引用是元数据。逻辑连续不要求物理连续：

```
逻辑块0 → 物理块7
逻辑块1 → 物理块21
逻辑块2 → 物理块13
```

"还能读到旧字节" ≠ "仍被有效结构引用"；后者才决定能否回收。

## 4. LittleFS 的元数据对与 CTZ

- 用两个块组成 **metadata pair**，小更新以追加提交，旧提交仍可作为恢复依据；
- 空间不足时整理有效信息、准备另一块、可靠交接（compaction）；
- 恢复时看修订号 + 有效提交，**不能只选最大修订号**。

**CTZ（copy-on-write 链）**：块引用方向从尾部向前，改靠前的块需要复制后面的内容。

```
追加：新元数据 → E → D → C → B → A     （只写新块）
改 B：新元数据 → D′ → C′ → B′ → A       （B 之后都要复制）
```

**结论**：小文件"改一下"可能触发多次复制；"只追加"也不等于只写几个字节（尾块未满时仍会复制尾块）。

## 5. 写放大、磨损均衡、垃圾回收

- **写放大** = 实际编程字节 ÷ 业务新增/修改字节（擦除次数单独统计）；
- **磨损均衡**：避免擦写集中，不代表总工作量下降；
- **GC**：让失效空间重新可用，不能缩小仍必须保留的数据。

LittleFS 用统计性动态磨损均衡：不保证各块擦除次数相同，也不为均衡搬所有冷数据。
空闲空间越少，分配与轮换选择越少——**满了以后别指望 GC 创造空间**。

## 6. 容量预算：算稳态 + 更新峰值

容量 = 有效数据 + 元数据/块内剩余 + **更新周转** + 余量 + 独立分区。

典型算例（仅示例）：

| 项 | 假设 | 容量 |
|---|---|---|
| 日志 | 24 B/条，1 条/分钟，保留 7 天 | 236 KiB |
| 历史 | 8 KiB/天 × 7 天 | 56 KiB |
| dump | 2 份 × 4 KiB | 8 KiB |
| 管理开销 | 需验证 | 32 KiB |
| 更新周转 | 按最大更新路径验证 | 256 KiB |
| 余量 | 非通用比例 | 128 KiB |
| 独立配置区 | 示例 | 8 KiB |
| **合计** | | **≈724 KiB** |

**注意**：写后文件大小不变，也可能因为缺周转空间返回 `ENOSPC`。

## 7. API 的承诺：write / sync / close

| 调用 | 承诺 |
|---|---|
| `write` | 返回成功 ≠ 落盘；可能已触发缓存刷出与硬件访问 |
| `sync` | 只提交**该文件**的待提交状态；不等于全局事务 |
| `close` | 可能先同步再释放资源，**也可能失败**；失败后不能假设句柄可继续用 |

**规则**：多个文件各自 sync 成功，不构成整体原子。

## 8. 重试、幂等与业务一致性

"收到请求 / 可靠保存 / 返回成功"是三个不同事件。
保存成功但响应丢失 → 重试可能重复追加、重复计数。

- 设置绝对值通常比增量更幂等；
- 追加类记录用业务 `record_id` 去重（同 ID 同内容返回既有结果）；
- 响应要区分"已接收/入队"与"已可靠保存"。

## 9. 并发：每次调用安全 ≠ 整套操作安全

例：A、B 同时读到"心率开、血氧开"，A 写"关、开"，B 用旧快照写"开、关" → A 的更新丢失。
每次写入都成功、CRC 都对，但结果错了。

**规则**：业务锁要覆盖"读—改—写"全过程，而不只是锁读或锁写。

## 10. 故障分层：别把不同层的问题混在一起

| 现象 | 判断边界 |
|---|---|
| 未提交的 RAM 记录消失 | 不等于文件系统损坏 |
| ENOENT / 正常 EOF | 不等于坏块 |
| 业务 CRC/长度错误 | 文件系统可能正常，按业务恢复策略处理 |
| 元数据提交中断 | 文件系统尝试识别有效提交，不保证任意损坏可恢复 |
| EIO/通信异常 | 还要区分供电、总线、保护、驱动、地址错误 |
| ENOSPC | 可能是有效数据/元数据/COW 周转不足 |

## 11. 定位"Flash 卡顿"的正确顺序

```
App 发起 → 协议/队列 → 业务锁 → 文件系统（FS 锁/分配/驱动/擦写/提交）→ 编码/发送
```

- App 超时只证明端到端没完成，**不能直接归因 fs_write**；
- `fs_sync` 慢可能包含尾部复制、编程、擦除、提交、等设备；
- 测量要区分"包含时间"与"独占时间"，别重复相加。

需要记录的量：每次事务的阶段时间、各 API 耗时与返回值、底层读写字节与擦除次数、锁等待、RAM 待写量、固件版本与场景。

---

**一句话结论**：Flash 的性能问题，多半不是"写得太频繁"，而是"每次写的东西比你以为的大"。
